01 · The flow & the master register

Thirty-four yeses light one flow

This section is the working heart of the document: one payment flow, sixteen node archetypes, and every datasource that must be granted before the flow can be lit. Each row names the ask, the person who must say yes, and the test the row has to pass before anything is collected from it.

A datasource confirmation is three things, never one: a named ask written in the customer's own vocabulary, a named human who can grant it, and an acceptance test that says when the row is finished. A row with an ask but no grantor is a wish; a row with a grantor but no acceptance test is a meeting that will be held twice. The register below carries all three columns for every row, and the pill at the end of each row is the only place the project reports progress.

There are thirty-four datasource rows and fifteen estate-wide rows — not seventy, and not four hundred. The full delivery programme (A1 through H7) lives in the Blueprint's procedures section (§10); this register holds only the rows where somebody outside Adeptio must grant something. Build tasks, collector configuration, parser work and dashboard assembly are Adeptio's problem and appear nowhere here. If a row is on this page, a customer or partner signature stands between it and data.

The register spans every collection lane in §03. Live lanes for this flow are L1 synthetic probes (6 rows), L2 protocol polling (6), L3 log streams (7), L4 API pulls (3), L5 file feeds (3) and L6 read-only DB queries (5). L7 manual import carries history alone (DS-34), L8 stays elective (DS-02), and two rows use techniques that are not lanes at all — an on-error capture (DS-17) and a network-flow edge (DS-25) tagged confidence=flow so it can never render as a flawless success rate (§04).

Rule R5 governs how a refusal is read: any one lane is enough to light a node. A row that is declined does not dim a node on the map — it lowers that node's stated confidence and its printed coverage number, and the screens above it keep their shape (§03). That is why every ask on this page can be answered with no, and why none of them can be answered with silence. Retargeting this reference flow onto MMPay, CB Bank or A Bank is a renaming exercise plus this prerequisite audit, never a redesign (§04).

How to read the register. ID is the permanent reference used by every other section of this document. Node gives the archetype and the reference example beneath it. Lane is the collection technique from §03. What it yields is what the estate gains if the row is granted; The ask is the sentence to put in front of the grantor, with the technical nuance folded into an expander. Grantor names the accountable role, Phase the §10 work item, Effort the honest cost to the customer's team.

The Status pill is clickable and cycles pending → asked → granted → verified → blocked → n/a; it is stored locally, so this page doubles as the tracking sheet for the confirmation meetings. Eight rows are striped in coral: those are the ones that historically slip, and every one of them is owned outside IT — a telco contract, a biller sandbox, a seeded funded account, a CAB-gated log format.

02 · Lens System & devices

Nothing is installed — the estate already emits most of it

This lens answers the question a platform, network or system engineer asks in the first ten minutes: what will this thing actually do to my device? Read it as the device-side contract behind §01's register — what we read, what we ask you to switch on, which port and which account, and what is never done to a box you own.

For rung 1 of every screen the answer is: nothing is installed (§02). No APM agent, no kernel module, no sidecar, no vendor daemon on a production host. Collection happens from a hardened collector host that lives in your zone and either pulls from an interface the device already exposes, or receives what the device already writes. The device gains no new software, no new listening service and no new outbound path.

That is possible because the flow's evidence already exists. A gateway writing no access log is rare; a gateway writing an access log in a shape nobody agreed is normal. An appliance that cannot speak SNMP is rare; one whose read-only view was never scoped is normal. A replica with no engine statistics is rare; one with no read-only role is normal. So the ask across all thirty-four rows is overwhelmingly a format, an account or a route — not an installation (R5: any one lane is enough to light a node, so a device that can only give one of the three still lights its node).

Collector-outbound, on a schedule, rate-capped.

SNMPv3 walks against a scoped view L2, an exporter scrape on a management NIC, a read-only JMX port, a timeout-capped SELECT on a replica L6, an API read token L4.

Touches the device: one authenticated read session per interval. Never touches it: no write, no SNMP set, no agent, no shell, no query against a primary.

Receive

Source-outbound push — the device decides when.

TLS syslog from appliances L3, a node shipper reading a log file the service already writes, a landing directory listed over read-only SFTP L5, and the lane that needs no device at all: an export file from a tool you already run — DS-34 L7, no credentials, no connectivity.

Touches the device: a forwarding target and a log format. Never touches it: no inbound session from the monitoring zone, no plaintext 514 accepted.

Probe

Synthetic traffic from three vantages L1.

Two internal vantage VMs (DMZ and app zone) plus one host on a domestic telco circuit — DS-04. Journeys run on seeded accounts: DS-01 the Pay Bill journey, DS-10 a login that is never locked out.

Touches the device: requests indistinguishable from a customer's, tagged so they stay out of the SLA denominator, with a rate and a timeout per E4 (OWASP API4). Never touches it: no load generation, no production OTP short code, no unbounded scan.

The only new box is the collector. One hardened host per zone (EW-12), placed where the signed zone diagram permits (EW-03), with disk sized at ≥72 h × your measured volume × 1.3 — which is why one week of du on three named directories is a Phase A item and not a nicety (EW-02). Local constraints drive that sizing: with daily power rotation, buffers are on disk with storage.sync full, never memory, and UPS state is polled as a signal in its own right so a scheduled power window is suppressed rather than reported as an outage (EW-10). Clocks are anchored per site because a thirty-second skew across sixteen nodes inverts the root-cause ranking silently (EW-04, §07).

A source that reaches gate 2 and stops is not a failure. It is an honest partial, the registry records acceptance_state, and the node carries onboarding on its face rather than a colour it has not earned (§10). The delivery lead's job at T−1 w is not to have every row green — it is to have every row's state true.

Five things stall this rollout in week one more often than anything else, and each has a prepared answer that costs nothing if it is applied early and two weeks if it is not (§10).

1 · The CAB cycle is four weeks, not two. Everything in Phase C queues behind one board meeting. Table the log-format and request-id package at T−4 w in Phase A, split the account and firewall packages so they travel separately, and get "add a probe target or poller to an approved collector" pre-approved as a standard change (EW-07 · H5) so Phase E never waits on the board at all.

2 · Nobody measured the log volume. 5 GB/day versus 50 GB/day is a 10× difference in disk and a different store topology, so the hardware is ordered against a guess. EW-02 (A2) requires seven daily du figures on three named directories — gateway, orchestrator, core banking — before any VM is requested, and D2 sizes every buffer from that number with the formula written down.

3 · The gateway is not the product everyone said it was. "Issue the request-id at the edge and echo it" is opposite work per product: Envoy sanitises an inbound x-request-id by default, Kong's correlation-id honours an existing header. EW-08 (A9) names product, version and config repository in week one, and the C3 change ticket is not drafted until that answer is in writing.

4 · The buffers were memory-only, and then the power went out. Every shipper in this class defaults to memory buffering, which survives a link cut and not a power cut — and here the power cut is a scheduled daily event. D1 sets storage.sync full, storage.checksum on and an explicit storage.total_limit_size before the first source is switched on (EW-12), and D9 makes UPS state a monitored signal so a power window is suppressed rather than reported as an outage.

5 · The evidence for the first real incident had already expired. By the time an error is detected, the thread states, retransmits, GC pauses and pool exhaustion that caused it are gone; a trigger that starts recording records the aftermath. The ring buffers are a standing Phase D prerequisite, not a Phase G nice-to-have — D7 turns them on, D8 books the one JVM restart window Flight Recorder needs (DS-17), and C9 removes journald's default rate limit, which otherwise drops 10 000 messages per 30 seconds during exactly the storm the capture was written for.

What "done" means. Done is not thirty-four green rows. Done is every row in §01 carrying a true state: verified against its acceptance evidence, or consciously blocked or n/a with the fidelity consequence written next to it and initialled by the person who declined it. That is R5 working as designed — any one lane is enough to light a node, so a refused ask never darkens the map; it lowers the node's fidelity and the map says so, on its face, beside an honest coverage number.
