Team Intake — Information-Gathering Meeting Note

Adeptio Pulse v2.0.4 · Pay Bill estate · 16 monitored objects · 6 session zones · 4 owning teams

This is a meeting note, not a change request. Adeptio Pulse is an APM-free monitoring overlay for the bank's Pay Bill estate: it reads only what your systems already emit — endpoints you already expose, logs you already write, APIs you already run, files you already drop — and correlates that evidence into monitored relationships on one map. To do that, Pulse needs a small, named set of things from each owning team: an endpoint or a directory, a read-only credential or none at all, a field definition, a person to call. This document walks every one of the 16 objects, states exactly what we will ask your system for, exactly what command class we will run against it and how often, and the expected result we will hold it to — so that each team can grant, scope, or refuse each item on the record in one sitting.

The standing claim

Pulse installs nothing on your systems. Every collection method below is read-only: we poll health endpoints you already publish, read logs you already write, call APIs you already operate, and list files you already drop. No agent, no APM library, no bytecode injection, no code change, no configuration change, no schema change, and no write — with one named, approved exception: the core heartbeat transaction, which posts only into the test account your team designates, at a value your team caps, and which you may refuse. If a read is refused, Pulse records that objective as not covered and paints the affected relationship grey. It never works around your control.

Meeting agenda

  1. Intro (10 min) — what Pulse is, what it reads, what it will never do; the standing claim above, read aloud and challenged.
  2. Walk the node blocks (25 min) — for each object in your chapter: identity, what we need from you, what we will run, expected result, and which monitored relationships the evidence corroborates.
  3. Capture responses (15 min) — fill the FORM FIELDS rows per object; name a PIC per object; record every constraint and objection in the object's own row, not in a side note.
  4. Confirm actions + windows (10 min) — agree the exact command classes, their cadence, the test window for the first run, and who is on the bridge for it.
  5. Sign-off (5 min) — chapter sign-off name and date in §E; anything unresolved is written as an objection, never left blank.

How to fill this document

Fill only the FORM FIELDS rows. Everything above them is what Pulse already intends to do; if a stated fact about your system is wrong, strike it and write the correction into "Constraints or objections" — do not leave a field blank. "Not granted" and "Not applicable" are complete answers; an empty box is not.

Vocabulary note

Lines on the Pulse map are monitored relationships. Pulse performs read-only collection and builds correlated evidence at each end of a relationship. Evidence carries one of three classes per relationship: CONN (reachability between the two objects — bound to the pair), APP (availability and response time at one object), LOG (error, decline and failure counts at one object).

NETWORK TEAMZ2 · ACCESS NETWORKZ5 · PARTNER DELIVERY NET4 objects

NETWORK TEAM owns both ends of the wire: Z2, everything between the customer's handset and the bank's perimeter (telco, edge), and Z5, the transport out of the bank towards the carrier and the aggregator (smsgw, bhub). The command classes are the transport verbs already written on your nodes — curl -w, dns probe, http poll against the public and hub VIPs, snmp, and smpp ping — reachability checks and read-only counter reads, run from a probe vantage; nothing is installed on a network device and no configuration is changed.

Cross-team exceptions

Four cross-team exceptions run through this chapter. NETWORK supplies and keeps alive the 4G APN vantage that Z1's client synthetic runs from — you own the vantage, DEV owns the script and the store-API token. bhub is the documented DEV object inside a NETWORK-chipped zone: the chip routes only the first command (reachability and transit to the hub VIP) to you; once transport is proven, the adapter-error and biller-timeout logs hand straight to DEV. smsgw is a split object — smpp ping is yours, dlr api is a read-only pull against carrier-supplied credentials and needs PARTNER coordination. And when the Z6 biller curl echo fails at TCP/TLS level rather than returning an error body, that is an outbound route or firewall problem and comes to NETWORK first, partner second.
